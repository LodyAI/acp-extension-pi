# Pi 1.4 runtime

Status: implemented
Translation: current

[中文](2026-10-28-pi-1.4-runtime.zh.md)

PR: https://github.com/LodyAI/acp-extension-pi/pull/26

## Abstract

The adapter pins Pi 1.4.0 with the same RPC adapter, extension selection and ACP-owned
MCP configuration as 1.3.0. Pi 1.4.0 changes provider model catalogs, summary output
limits and classifier image input; it adds no RPC command, session field or extension
hook the adapter uses. The source change is the dependency pin, the advertised RPC
contract version and this note. Lody still needs a separately built, checksummed
managed runtime before installed providers receive it.

## Decision

Bump the exact `@earendil-works/pi-coding-agent` pin from 1.3.0 to 1.4.0 and update
`PI_RPC_VERSION`, which the adapter reports as its `agentInfo` version. Do not add a
version detector, compatibility branch or fallback: the pin is exact, and an external
`LODY_PI_PATH` runtime must implement the same 1.4 contract.

Pi 1.4.0 keeps the 1.3 RPC commands the adapter drives (`get_available_models`,
`get_available_thinking_levels`, `set_model`, `set_thinking_level`, prompt, steer,
abort, compaction and stats), so the adapter's wire contract and tool behavior stay
compatible. It does not pin a model list: it reports whatever the launched Pi
version exposes.

Against the same `~/.pi/agent` profile, 1.4.0 makes one model available that 1.3.0
did not, `opencode-go/minimax-m3.1-flash-free`, and drops `cat-jam-free`,
`space-bunny` and `step-5-preview-free` from OpenCode Go. 1.4.0 also adds
`MiniMax-M3.1-Flash` to its built-in `minimax` and `minimax-cn` catalogs, which
only appears for a profile that configures those providers.

`generateSummary()` ignoring `reserveTokens` and provider attribution headers are
internal to Pi's model requests and need no adapter work. Native behavior did change
where the adapter does not re-implement it: a third codemode script now waits for a
free worker instead of failing, and resuming a branch can activate extension tools
that were registered after the branch was recorded. The adapter contract is
unchanged and the existing unit, wire and smoke suites still pass, but this is
compatibility, not identical native behavior.

## Evidence and validation

- `pnpm check` (typecheck, 111 tests with one Windows-only skip, Prettier) passes on
  Node 26.11.1 macOS arm64.
- `pnpm build` and `pnpm smoke` pass. The smoke drives the official 1.4.0 CLI through
  the deterministic local model in both ordinary and codemode-only modes, including
  MCP text/errors/images, questions, todos, native session list/load, subagents,
  Stop/recovery and explicit extension selection.
- `pnpm pack` plus an installed-tarball smoke pass, matching the Check workflow's
  packaging steps.
- Calling 1.4.0's `ModelRuntime` with the existing `~/.pi/agent` configuration
  returns 35 available models (OpenCode Go 33, Volcengine Agent Plan 2), while Pi
  1.3.0 returns 37 from the same configuration. The only additions and removals are
  the four IDs listed above; the difference is the catalog, not Lody's capability
  cache.
- A synthetic codemode probe that occupies both workers observes 1.3.0 failing the
  third script with `worker limit reached` and 1.4.0 queuing it until a worker is
  free. The adapter never implements that scheduler, so no adapter change follows.
- The adapter's `supportedThinkingLevels` matches Pi 1.4.0 for all 1,599 built-in
  chat models, so the thinking ladder it derives stays correct as model data moved.
- `initializeResponse().agentInfo.version` is now asserted against the installed
  Pi's exported `VERSION`. Reverting `PI_RPC_VERSION` to 1.3.0 fails that assertion;
  before it existed the full suite still passed with the drift.

## Ablation

- Removing the `package.json` pin while the lockfile keeps 1.4.0, or removing the
  lockfile's `pi-coding-agent@1.4.0` package entry, makes
  `pnpm install --frozen-lockfile` fail. Both hunks are load-bearing.
- Removing the `src/version.ts` hunk passes every pre-existing check, so the wire
  assertion above exists to make that removal fail.
- The README and note hunks are documentation: no check depends on them, and they
  are kept only for accuracy and the decision record.

## Limits

- No Electron desktop run and no commercial model request were part of this change;
  earlier desktop and real-model evidence remains tied to the 1.3 runtime PR.
- The managed runtime archive, its checksums and the Lody-side manifest are produced
  and validated by the operator packaging pipeline. This note does not claim public
  artifact publication.
- The Check workflow's Linux and Windows x64/ARM64 results must be read at the actual
  PR head; local validation covers macOS only.
